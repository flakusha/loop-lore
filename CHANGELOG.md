# Changelog

All notable changes to loop-lore. Format: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), versions per [SemVer](https://semver.org/).

## [Unreleased]

### Added

- **Emotion-avatar panel gains re-roll and regenerate-all controls** — the character edit page's emotion-avatar panel now exposes what the API already had: every `EmotionType` in the picker (the hard-coded happy/sad/angry/surprised/neutral subset is gone), an optional base-seed field with a "reuse the seed recorded for this actor" toggle, "Regenerate all" (re-rolls every base emotion slot through `replace: "slot"`), "Regenerate selected" (the picked subset) and a per-variant "Re-roll" button, plus the actor's current emotion variants. The client calls the existing `POST /actors/:actorId/emotion-avatars/regenerate` endpoint with `seedStrategy: "reuse" | "random"` and the explicit seed — no new endpoint. Two server gaps closed behind the UI: the actor-level batch endpoint now accepts `seed`/`seedStrategy` like the re-roll endpoint, and an empty `emotions` list falls back to the default emotion set instead of running a zero-slot batch that reported `completed` without producing an avatar (the wardrobe batch endpoint had the same hole). The wardrobe panel in the character page never loaded its outfits — the panel's mount tag (and its `x-init`) is stripped when the panel is inlined, so the load trigger moved to the panel heading. The duplicate panel copy under `src/components/chat/` is gone; `src/components/character/` is the single source.
- **Emotion-avatar generation records and reuses a seed** — every batch now runs under ONE explicit base seed (`src/characters/services/emotion-avatar-service/seed.ts`): the seed the caller supplied, the seed recorded for the scope when the caller asked to reuse it, or a fresh random base. Each emotion slot derives its provider seed from the base via the stable `EMOTION_ORDINAL` offset, so a variant keeps its identity across runs and a single-slot re-roll reproduces that slot alone. The base seed is persisted with the job (`generation_jobs.payload.seed`) and the slot seeds in the job's result entries; `findRecordedBaseSeed` reads the newest one back, scoped by actor and by outfit, so one actor's or outfit's seed never leaks into another's. Callers can pin a seed or reuse the recorded one (`seedStrategy: "reuse"`) from the actor-level batch endpoint, the regenerate endpoint and the wardrobe generation endpoints, and an out-of-range seed is rejected instead of forwarded to the provider. Storage rides on the existing free-form JSON columns — no migration. The `sdcpp` and `comfyui` engines forward the seed to the backend; the `openai` and `sdapi` engines ignore it, so there the recorded seed pins the value but not the pixels.

- **Chat variant taxonomy reaches the user** — the canonical `(chat_type, chat_mode, chat_purpose)` table (`src/chat/types/variants.ts`) finally has a path from the UI: every variant is selectable in the new-chat form, and the server pins the triple plus the auxiliary columns (`max_turns`, `auto_advance`, `gm_config`, `talkativity`, `prompt_override`) from that one table, so the client no longer re-derives the taxonomy. An explicit `null` override survives instead of silently falling back to the variant default, a chat-setup template no longer overrides the chosen variant, the variant talkativity is seeded on every participant rather than the owner alone, the llm-only variants carry a real validation prompt, and the form's type/mode controls go inert while a variant is chosen (the RPG variants additionally require a world). The duplicate client-side taxonomy is gone; the entry-point tab branching and the legacy-chat backfill stay open as cross-cutting work in `epic-chat-variants-taxonomy`.
- **`typecheck - bun` gate type-checks `tests/**` for the first time** — Bun 1.4.3's built-in TS7 checker (`bun --check`) runs against the root `tsconfig.json`, whose `include` is `src/**` ∪ `tests/**`. No other gate touched `tests/**`: `typecheck - backend` is `tsconfig.backend.json` (`src/**` minus `src/frontend/**`), `typecheck - frontend` is `src/frontend/**`, `typecheck - scripts` is `scripts/**`, and both `type-coverage` gates score the backend/frontend projects. Verified by planting one TS2322 in `tests/` and running every typecheck gate — `typecheck - bun` was the only failure. ~1.1s, so it also rides along in `check:fast`. Adopts the `bun` binary that was already the runtime and changes no dependency position: `bun --check` cannot select a project and silently skips `scripts/**`, so it complements rather than replaces the `tsgo` gates. The name `bun check` stays unusable (the `check` script shadows it and the gate would pass vacuously) — the spelling is `bun --check`.
- **Tagged error infrastructure** — `src/errors/tagged.ts` defines the `TaggedError` base (plain `Error` subclasses carrying a literal `tag` discriminant, deliberately not `effect`'s `Data.TaggedError` — no `Effect` pipeline exists at any throw site, so the effect coupling would buy nothing; the header comment records the judgment) plus an `isTaggedError` guard, `TagOf`, and `assertNeverTag`. A family exports its failure union and an exhaustive mapped-type status record — `{ [E in FamilyError["tag"]]: number }` — so adding a variant without an HTTP mapping fails to compile. The actor-items gameplay service (`src/services/actor-items/errors.ts`) and the characters import/export family (`src/characters/errors.ts`) are the canonical conversions: equip/unequip/transfer denials now throw `ItemNotFoundError`/`SlotConflictError`/`AffordanceDeniedError`/… instead of stringly `ok: false` results whose optional `reason ?? "fallback"` could silently mask a missed case, and `handleImportExportError` maps by tag rather than by `ErrorCode` with a `default: return 500` catch-all.
- **Shared exponential-backoff helper** — `src/utils/backoff.ts` (`exponentialBackoffMs({ baseMs, attempt, capMs })`, 1-based attempts, optional cap) replaces the copy-pasted `base * 2 ** (attempt - 1)` curves at the proactive-messaging timing helper, the tunnel reconnect delay (`src/frontend/alpine/tunnel-protocol.ts`), and the safe-fetch retry sleep. Consolidated in-process only: DB-persisted backoff (`src/federation/outbox.ts`) keeps its inline formula on purpose, and `Effect.Schedule` was rejected because two of the three sites are pure delay calculators with no retry loop to drive.
- **VN decisions block free-sending until resolved** — a VN chat that opted in (`gm_config.vnChoicesEnabled`) with an unresolved branching choice or Q&A question now returns `409` from `POST /api/chats/:id/messages` instead of accepting a free-send that ignores the pending card. Server-side and authoritative (`enforceVnDecisionGate` in `src/routes/messages/guards.ts`), because a client-only gate is bypassable — `chat-quick-replies.ts` posts through the same path without touching the composer. Gated on the per-chat flag with a by-PK `chats.gm_config` read and an early-out, so a chat that never opted in pays one extra indexed lookup and nothing else. Placed AFTER the idempotency short-circuit on purpose: gating earlier would turn a retried POST into a `409`, defeating the exact retry the short-circuit exists to serve. `409`, not the `403` the mute gate uses — a pending decision is a state conflict, not a permission failure (precedent: `KeyMechanicConflictError`). Scope is the whole chat rather than the current scene: the send path carries no scene index, and a row left `available` at scene 0 is still dangling at scene 12.
- **Skip control for pending VN decisions** — the escape hatch, because a gate with no exit is a wedge. `POST /api/chats/:id/vn-choices/:id/dismiss` and `POST /api/chats/:id/vn-questions/:id/dismiss` (`dismissVnChoice` / `dismissVnQuestion`), plus a Skip button on both card renderers. Writes `status='dismissed'` rather than a `dismissed_at` timestamp — a timestamp would leave `status='available'`, so the pending query would keep matching and the chat would never reopen. The `dismissed` value is a terminal sibling of `selected` in `vnChoiceStatusMachine`; both are terminal because a decision resolves exactly once. Client side, `src/frontend/vn/pending-decision.ts` holds the one shared bit both card modules write and the composer reads, so the advisory client guard warns before the optimistic push instead of rolling a message back after the server already rejected it. `_autoFired` sends are exempt — the automated loop cannot answer a card, so gating it would deadlock its own consecutive-fire guard — and slash commands (`/continue`, `/retry`, `/branch`) keep working: the gate blocks free send, not the command surface.

- **Per-chat VN choice opt-in** — `gm_config.vnChoicesEnabled` (default `false`) gates the branching-choice and Q&A card surfaces. Off by default, so a VN chat no longer pays two HTTP GETs per scene render (`/vn-choices` and `/vn-questions`) for cards nobody opted into. The gate is on the _mount_ predicate in `renderCurrentScene`, not a hide-after-render: mounting and hiding would still cost the round-trips. Unlike every sibling VN setting, the flag deliberately does NOT fall back to localStorage — it is a per-chat permission, and persisting it client-side would leak one chat's opt-in into the next. It is allowlisted on both the server (`chat/service/access.ts`) and frontend (`gm-config-presentation.ts`) sides and declared in `GmConfigSchema`, all three of which are required for the value to survive a round trip; a `gm-config.test.ts` parity test compares the two allowlists directly so a one-sided edit fails CI.
- **VN Q&A interaction loop** — questions a character asks inside a VN scene, and the answer the player picks. `vn_questions` table (migration `047`, modelled on `vn_choices`: same impact columns, available/answered lifecycle, chat cascade, no FK on `speaker_id`); service layer `src/chat/service/vn-questions.ts` (`listVnQuestions`, `answerVnQuestion`); guarded routes `GET /api/chats/:id/vn-questions?sceneIndex=N` and `POST /api/chats/:id/vn-questions/:qid/answer` (`src/routes/chats/vn-questions.ts`); LLM generation `POST /api/chats/:id/vn/generate-questions` (`src/routes/vn-generate/questions.ts`, persisting before returning like the choices path); prompt purpose `vnQuestions`; frontend cards `src/frontend/vn/question-cards.ts` + `question-cards-render.ts` (native `<button>` options, per-side-effect try/catch so a failed location PUT never loses the recorded answer).
- **VN scene templates applied at render time** — `src/frontend/vn/templates/apply.ts` maps a scene's `templateId`/`templateVars` onto the effective render settings, called at the top of `renderCurrentScene` so all five render paths (init, next/prev, jump, add) pick it up. Merges only `layout`, `imageScaling`, `transition`, `typewriterSpeed`; `resolveVariables` throwing on a missing required variable falls back to the base settings, and the transition is whitelisted against `VnSettings["transition"]` — an out-of-union value (the built-in `"fade-in"`/`"none"`) would otherwise leave the scene at `opacity: 0` forever.
- **Hot-apply config updates without restart** — a config change (fs watcher edit or an API write) now re-applies to running consumers without a restart. `src/config/hot-apply.ts` diffs the new `Config` against the previous snapshot, classifies every changed leaf path against an explicit registry (`HOT_APPLY_PATHS`), and emits a `ConfigChange` to subscribers (`onConfigChange`). `src/config/hot-apply-consumers.ts` maps registry entries onto the runtime stores that consumers actually read: `logging.level` → `Logger.setLevel` (now mutable on `LoggerImpl`/`LightLogger`), `nsfw.allowNsfw`/`nsfw.nsfwMinAge` → the NSFW runtime store, `ageGate.enabled`/`minimumAge`/`mode` → the age-gate runtime store. Restart-required paths (server port, DB dialect, auth, transport, provider registry, …) default to `restart` and are surfaced to the admin UI: `GET /api/admin/config-schema` gains `hot_apply_paths`, and `PATCH /api/admin/system-config` returns `requires_restart`. Wired in `src/server/start.ts` (snapshot seed + consumer subscription + watcher callback).
- **Plugin UI mount points (FEAT-050)** — `GET /api/plugins/ui-components` (admin) lists registered UI components with an optional `?location=` filter. Web-capable components (`type` `web`/`both`) mount as inert host containers carrying `data-plugin-component` / `data-plugin-location` and HTML-escaped `props` JSON into `chat.header` / `chat.sidebar` / `chat.composer` (`src/views/chat.html`) and `admin.dashboard` (`src/views/admin.html`); TUI-only components are never mounted into web views.

- **Wardrobe / loadout avatar variants** — outfit-scoped character appearance layered onto emotion selection: migration `031_wardrobe.ts` (`wardrobe_items`, `actor_wardrobe` bindings, `chat_wardrobe_overrides`, `character_avatars.outfit_id`, `world_avatar_config.outfit_bindings`), selection ladder v2 (chat override > location rule > flag-gated equipped-loadout bridge > character default, then (outfit,emotion) → (outfit,neutral) → (default,emotion) → base), wardrobe CRUD + per-outfit avatar generation routes (`/api/v1/actors/:id/wardrobe[...]`, `/api/v1/chats/:id/wardrobe-override/...`) with central TypeBox validation and owner/participant auth, outfit-change immersion-gate seam (`requestOutfitChange`; NPC/world-rule bypass), `outfitContext` prompt section, character-sheet wardrobe manager panel (outfit CRUD + variant grid grouped by outfit × emotion) and chat-header outfit switcher, and a default-off `system_config.wardrobe_loadout_bridge` flag that lets equipped inventory bindings auto-select the outfit at resolve time (read-side only — no equip-time writes).
- **Chat archival workflow** — `archive_retention_days` admin setting (default 90) with admin route, daily GC sweep (`src/gc/archive-expiration.ts`) registered on cron `0 3 * * *`, asset-cascade via new `asset_links.archived_at` column + migration `017_asset_links_archived_at.ts`, purge route `DELETE /api/chats/:id/purge`, archived-chats filter in list/get queries, soft-link/unlink asset helpers, and `chat.archived` / `chat.unarchived` / `chat.purged` plugin events.
- **Assistant tooling (D3/P2-C)** — `/rewrite` and `/translate` (`/tl`) commands with style/language parsing, expanded command palette entries, multi-step creation wizard (edit → options → review), command button toolbar with GM-role filtering, ownership indicator badge on user-authored messages.
- **Shared interaction ledger** — dice-backed game interactions now persist roll math, ability and relationship modifiers, successful/failed/blocked outcomes, and state changes in `interaction_logs`; social reference commands update canonical character relationships and feed recent-interaction prompt context.
- **Actor autonomy — story auto-drive scheduler** — `AutonomyScheduler` (`src/autonomy/scheduler/`) drives the world-tick loop: `tickOnce(nowMs)` selects due worlds, dispatches each through the existing `runNpcMovementTick` pipeline (no new dispatch path), and commits the per-world cursor from the resolved `AutonomyConfig.tickIntervalMs`. `pause(worldId)` / `resume(worldId)` / `stepOnce(worldId)` / `stateFor(worldId)` give ops human-in-loop control. Due-world ordering is `(next_tick_at ASC, world_id ASC)` — total and restart-stable, since `world_id` is unique. Cursor, pause flag, tick count and last error persist in the new `world_simulation_state` table (migration `023_world_simulation_state.ts`); the cursor write is the commit point, so a crash replays at most one world tick. Telemetry: `scheduler.world_tick.started` / `.completed` / `.error` with the world/payload envelope. Cadence is the caller's job — real-time, accelerated and manual sources all reduce to repeated `tickOnce`; the `giwt sim` CLI is a separate ticket.
- **Emotion-avatar batch progress over SSE** — `GET /api/v1/actors/:actorId/emotion-avatars/jobs/:jobId/stream` streams `{ jobId, done, total, status }` per variant (`progress` events, a terminal `done`, 15s keepalives), with the same `checkActorOwnership` + job-belongs-to-actor guard as the sibling job routes. The character emotion-avatars panel shows a live progress bar from an `EventSource` per active job and keeps its 2s polling loop as the fallback; streams close on terminal status, on actor switch, and on error.
- **Opt-in regex precision telemetry** — per-pattern call/match counters behind `TELEMETRY_REGEX_PRECISION=1` (off by default, and forced off when the events sink is off), flushed every 60s as one `regex.precision` event per pattern. Stable pattern labels and aggregate counts only — no message content, targets, or match text. Instrumented at the `action-parser` verb/target sites and `workflow-routing` intent groups.

Blocking rather than ADVISORY on purpose — the check is deterministic over tracked files and cannot drift from a concurrent dev merge (same rationale as `tests - coverage gaps`).

### Changed

- **TS7 toolchain review — no dependency dropped, and why** — evaluated dropping the TypeScript-7 migration dependencies now that Bun 1.4.3 ships `bun check` (a port of the same `typescript-go`, 51,210/51,210 TS7 conformance). Conclusion: `typescript@^5.9.3` must stay — `typescript-eslint@8.71.2` peers `>=4.8.4 <6.1.0`, and TS7's default export is a version-only stub (`exports["."]` is `lib/version.cjs`, so the API moved to `./unstable/*` — a rewrite, not a bump, for `type-coverage-core`, `scripts/check-file-size.ts` and `scripts/lib/src-refs.ts`); `type-coverage-core@2.30.4` is still broken on `ts.SyntaxKind.Unknown` (`dist/checker.js:669`). `@typescript/native-preview` could in principle be retired by `bun check`, but the name is unusable here: a script named `check` shadows the built-in, so the command resolves to the gate runner and **exits 0 having type-checked nothing**. The documented escape hatch `bun --check` is also not a drop-in — it cannot select a project, and a planted type error under `scripts/` passes it (exit 0) while `tsgo -p tsconfig.scripts.json` catches it. Full evidence and the unblock conditions in `docs/meta/tooling/ts7-bun-check-review.md`; the stale TS7 note in `docs/meta/code-practices-improvements/01-strict-typing.md` is corrected to match.
- **Check-runner default concurrency raised to 4, on measurement** — `DEFAULT_JOBS` in `scripts/check/parallel/runner.mjs` was 1 on the assumption that concurrent gates OOM this host. Measured during a real `giwt finalize` at JOBS=1 (61 GiB total, 52.3 GiB available, 32 cores, zram `/tmp`): peak **11.93 GB** total RSS and **2.79 GB** for the single heaviest process (`tsgo`) — so JOBS=1 already burned a quarter of available RAM through one gate's own child pool, and the serial default was not buying the safety it was assumed to buy. At JOBS=4 the light pool's four heaviest gates sum to ~9.4 GiB (backend 3.1, coverage 2.8, scripts 2.4, knip 1.1) — no more than the serial run already reached, because a single `tsgo` gate spawns enough children to get there alone. The cap bounds the light pool only: every heavy gate is `await`ed one-at-a-time in a loop that never reads `JOBS`, so no value here can start two `bun test` processes. Wall time gains little — light gates finish in under 15s and the run is dominated by the serialized heavy gates (coverage 153s and e2e 145s medians) — so 4 buys headroom symmetry, not speed, and is marked measured-safe rather than measured-optimal: three concurrent finalizations on heavy gates is the shape still un-measured. AGENTS.md, the runner header, and `docs/meta/tooling/finalize-speedup.md` updated to match.
- **Diff-scoped eslint gate honors its cache** — `scripts/check/parallel/gates-scope.mjs` built the `--diff-base` eslint command as `bunx eslint --concurrency=4 <files>`, silently dropping the `--cache --cache-location .tmp/eslint.cache` that `package.json`'s `lint:eslint` carries, so every scoped run re-parsed the corpus cold. Finalize runs scoped, so the 19.4 GB cold peak the narrowing exists to avoid came straight back on the only path most agents take. The flags are restored and the scoped gate now warms a per-worktree cache (measured 1652 ms re-running the same 5-file diff). `HEAVY_NAMES`'s stale justification — which cited eslint at "~1.5 GB peak with `--concurrency=8`" while the measured cold figure is 19.4 GB — is corrected, and the `finalize-speedup.md` finding it contradicted is closed out.
- **Actor-items gameplay denials mapped by the tagged error boundary** — `src/routes/actor-items/service.ts` registers one `taggedErrorBoundary` (from the new `src/routes/http-utils/tagged-boundary.ts`) on the family instance instead of repeating `if (!res.ok) return badRequestResponse(res.reason ?? "fallback")` per endpoint. Failure statuses are now precise: unknown item `404` (was `400`), slot conflict `409` (was `400`), affordance denial `403` (was `400`); well-formed business denials (transfer self/quantity/insufficient) stay `400`. No frontend caller branches on the old blanket `400`. Any non-tagged throw in the family — DB loss, invariant violation — is logged under `routes.actor-items` and answered with a sanitized `500` that never echoes internal error text.

Import-specifier-only change, no behavior change.
