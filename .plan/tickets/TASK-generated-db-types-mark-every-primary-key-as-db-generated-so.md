# TASK: Generated DB types mark every primary key as DB-generated, so an id-less INSERT type-checks and stores a NULL id

**Status:** Done
**Priority:** high
**Effort:** Medium
**Caveats:** TOCTOU, security, authorization, parallelism, lock/unlock lifecycle, partial failure, rollback, stale state, data races, idempotency, observability

**Summary:**

**Summary:**\n\nThe DB type generator wraps EVERY primary-key column in `Generated<...>`, which makes Kysely treat `id` as optional on insert. An INSERT that omits `id` type-checks, and SQLite stores NULL because a TEXT PRIMARY KEY without a DEFAULT accepts NULL.\n\n**Mechanism:**\n\n- `scripts/generate-db-types.ts:274-277` — `if (col.primaryKey || (col.hasDefault && col.notNull))` returns the `Generated<base>` wrapper. The `col.primaryKey` clause is the hole: the manifest records `primaryKey` and `hasDefault` as separate flags (`scripts/generate-schema-manifest.ts:129-133`), so the generator already knows a TEXT PK has no DEFAULT and still claims one.\n- `Generated<T>` is Kysely `ColumnType<T, T | undefined, T>`: the column becomes optional in the insert object, so `typecheck - backend` (BLOCKING) cannot see the omission. Typecheck is not a candidate guard here — the generated type makes the bug legal.\n- In SQLite a TEXT PRIMARY KEY is not a rowid alias, so it permits NULL: the row is stored with `id = NULL` and every later `WHERE id = ?` matches 0 rows.\n\n**Instances:**\n\n- `src/assistant/commands/create-entity-lore.ts:182-199` inserts `world_lore_entries` / `actor_lore_entries` without `id`; the row lands with `id = NULL` and the cooldown write-back `WHERE id = NULL` updates 0 rows forever (BUG-assistant-created-lore-entries-are-stored-with-a-null-id-so-).\n- The notification writer is the same class of defect on another table (BUG-appeal-reversal-notification-is-stored-with-a-null-id-which-).\n- Scope: every no-default TEXT PRIMARY KEY column listed in `src/db/schema-manifest.ts` (about 145 TEXT PK columns).\n\n**Smallest check — fix the GENERATOR, not the generated file.**\n\n`scripts/generate-db-types.ts:275` should emit `Generated<base>` only when the DB actually supplies the value — `col.hasDefault`, or the INTEGER PRIMARY KEY rowid alias (primaryKey with an integer type) — and must NOT wrap a no-default TEXT PK. Such a table then types as `id: string`, which makes `id` REQUIRED in the insert object. Regenerate with `bun run db:sync-types`; the committed `src/db/schema-*.ts` and `src/db/generated/db-types.ts` are artifacts of that generator and `scripts/check-db-schemas.ts` (the `db - schema gate`) keeps them honest. The insert sites that relied on the hole must be fixed in the same commit.\n\n**Why the type change beats a static scan:** a script that flags `.insertInto(<table>)` whose column list omits `id` for a no-default-PK table has to re-derive the table set, parse insert column lists, and carry its own diff scoping and allowlist. The type change reuses the existing BLOCKING `typecheck - backend` gate: no new script, no baseline, no allowlist, and the signal is exact because the compiler sees the whole table type.\n\n**Diff-scoped:** yes, by construction. Typecheck runs the whole project, but only a changed file can introduce an id-less insert, so the signal is naturally limited to the diff. No gate narrowing is required.\n\n**Blocking vs advisory:** blocking through the existing typecheck gate. The generator rule change and the insert-site fixes must land together or typecheck goes red repo-wide.\n\n**Effort:** M — one generator rule, one regeneration, the offending insert sites, and a regression test asserting that a no-default TEXT PK is typed `id: string` with no `Generated` wrapper.

**Context:**

Why: the defect class (an id-less INSERT into a TEXT PRIMARY KEY silently storing `id = NULL`) is invisible to every existing gate. The generated type made the omission legal, so the only BLOCKING guard (`typecheck - backend`) could not see it. Two instances shipped as bugs (assistant-created lore entries, moderation-reversal notification).

Constraints:

- The fix belongs in the GENERATOR (`scripts/generate-db-types.ts`), never in the generated artifacts: `scripts/check-db-schemas.ts` (the `db - schema` gate) regenerates and diffs them, so a hand edit is overwritten.
- The generator rule change and the insert-site fallout must land in ONE commit. Flipping the rule turns every id-less insert into a compile error, so splitting them leaves the branch red repo-wide.
- `Generated<>` may only be emitted when the DATABASE supplies the value. The schema manifest's `hasDefault` flag cannot see the SQLite INTEGER PRIMARY KEY rowid alias, so the rule must also look at the column TYPE: keying it off `hasDefault` alone would make every INTEGER PRIMARY KEY an insert-time compile error even though SQLite fills it.
- Scope: the generator rule and the insert sites the compiler flags. The config-key-reader gate (issue 0be6465, ticket `TASK-no-gate-checks-that-a-declared-config-key-has-a-reader-so-wr-*.md`) is a separate ticket and is NOT part of this branch.

Alternatives considered:

- A static insert-site scanner (a script that flags `.insertInto(<table>)` whose column list omits `id`): rejected. It would need its own table set, insert-column parsing, diff scoping and allowlist — duplicating what the compiler already knows from the table type, and adding a new gate instead of reusing a blocking one.
- Weakening the type rule to accommodate an insert site: rejected. The generated type IS the guard; a site that cannot supply an id needs a real id, not a wider type.

**Resolution:**

Rule implemented in `scripts/generate-db-types.ts`:

- `dbSuppliesPrimaryKey(cols, colName)` (scripts/generate-db-types.ts:263-270) answers "does the DATABASE fill this primary key?". It returns true when the column has a DEFAULT, or when it is the SQLite INTEGER PRIMARY KEY rowid alias: the sole `primaryKey` column of the table whose type is `integer`, which SQLite auto-assigns with no DEFAULT clause. The manifest's `hasDefault` flag does not capture the rowid alias, so the column TYPE is part of the rule; keying it off `hasDefault` alone would make every INTEGER PRIMARY KEY an insert-time compile error.
- `tsType` (scripts/generate-db-types.ts:272-317) now wraps a primary key in `Generated<>` ONLY when `dbSuppliesPrimaryKey` says the database fills it. BEFORE: `if (col.primaryKey || (col.hasDefault && col.notNull))` returned the `Generated<base>` wrapper for EVERY primary key. AFTER: a primary key the database does not fill types as the plain base type (`id: string`), so Kysely's insert object REQUIRES `id` and omitting it is a compile error. The select type is unchanged (`string`, never `string | null`), so reads keep the type they had before.
- Non-primary-key columns are untouched: `hasDefault && notNull` still yields `Generated<...>`, nullable columns still yield `base | null`.
- `scripts/generate-db-types.ts:502-533` (test insert helpers) now requires a primary key the helper cannot mint. The helper mints `id`; every other primary key the database does not fill is a required member of the helper's `opts` object, so a fixture row can no longer land with a NULL id.
- Regenerated with `bun run db:sync-types`: `src/db/schema-{blog,character,content,core,crafting,generation,gm,moderation,story,synthetic,telemetry}.ts`, `src/db/schema.ts`, `src/test-utils/insert-helpers.ts`, `src/validation/db-schemas.ts`.
- Regression test `scripts/generate-db-types.test.ts` ("generated primary-key types", 6 assertions): a TEXT PK without a DEFAULT types as `string`; a PK with a DEFAULT types as `Generated<string>`; the INTEGER PRIMARY KEY rowid alias types as `Generated<number>`; a non-PK defaulted column is unchanged; the committed `src/db/schema-core.ts` types `users.id` and `user_api_keys.id` as `string` while `interaction_logs.id` stays `Generated<string>`.
- Insert sites fixed in the same commit: 29 id-bearing inserts across 18 files (every one supplied a real id): `src/chat/message-translations.ts` (message_translations), `src/generation/auto-gen/fire-random-event.ts` (chat_random_events), `src/worlds/conditions.ts` (world_condition_history), `src/worlds/timescale.ts` (world_timescale, world_timescale_history x2), `src/assets/controller.acl.test.ts` (asset_shares), `src/assets/service/delete.test.ts` (personas), `src/characters/services/shared-service-utils.test.ts` (actors x2), `src/generation/auto-gen/story-mode.coverage.test.ts` (location_states), `src/generation/providers/failover-key-scope.test.ts` (user_api_keys), `src/generation/providers/registry-branches.test.ts` (user_api_keys x4), `src/generation/providers/user-api-key.test.ts` (user_api_keys x2), `src/middleware/auth.test.ts` (sessions x8), `src/routes/worlds/autonomy-routes.test.ts` (character_internal_traits), `src/story/game-master.test.ts` (location_states), `src/story/whatif-simulator.test.ts` (world_timeline_events).
- The two already-shipped instances are fixed here too, byte-identical to the sibling branch `fix-review-findings` (same `uid` import and same `id: uid()` lines, so the two branches merge without a conflict): `src/assistant/commands/create-entity-lore.ts` (imports `uid` from `../../utils`, adds `id: uid()` to `loreValues` — the lore rows are addressed by id in the cooldown write-back) and `src/nsfw/moderation-service/appeals-reversal.ts` (imports `uid`, adds `id: uid()` to the notification row).
