# BUG: Appeal-reversal notification is stored with a NULL id, which hides the user's whole notification list

**Status:** Done
**Priority:** high
**Effort:** Medium
**Caveats:** TOCTOU, security, authorization, parallelism, lock/unlock lifecycle, partial failure, rollback, stale state, data races, idempotency, observability

**Summary:**

notifyModeratorReversal inserts into notifications without an id column, so the row is stored with id = NULL and the user's entire notification list stops validating on the client. Evidence: src/nsfw/moderation-service/appeals-reversal.ts:135-142 - insertInto('notifications').values({user_id, type, title, body, data}) with no id. It is the only production insert site that omits it; src/notifications/service/crud.ts:56-58 passes id: uid() and src/nsfw/moderation-service/audit.ts:140-141 passes id: crypto.randomUUID(). src/db/migrations/001_init.ts:127 declares the column as addColumn('id','text', col => col.primaryKey()) with no default and no NOT NULL, and SQLite permits NULL in a TEXT PRIMARY KEY (the NULL-is-not-distinct quirk only applies to INTEGER PRIMARY KEY) - probe-verified: the insert succeeds and stores id = NULL, and two such rows can coexist because NULL never equals NULL in the unique index. src/db/schema-core.ts:151 types the column as id: Generated`<string>` (generated by scripts/generate-db-types.ts:275, which wraps every primaryKey column in Generated because it assumes a DB-side default that does not exist), so the omission type-checks and no lint rule flags it. Downstream: src/notifications/service/crud.ts:15-27 mapRow copies the null id through; src/routes/notifications/index.ts:36-41 returns the item with id null; src/validation/schemas/responses.ts:168-174 requires id: Type.String() on NotificationListItem, so one null id fails the whole NotificationRefresh object; src/frontend/alpine/user-notifications.ts:63 parseOr(NotificationsRefresh, ...) falls back to {items: []} on validation failure, discarding the entire list rather than the bad row. The SSE stream (src/routes/notifications/stream.ts:141) ships the same poisoned item, so parseOr(NotificationsEvent) fails and the bell early-returns at src/frontend/alpine/user-notifications.ts:85 and never updates again. The row can never be cleared: PATCH /api/v1/notifications/:id and DELETE /api/v1/notifications/:id both filter on id, and id = NULL never matches (probe-verified: WHERE id = NULL matches 0 rows). Failure scenario: a moderator has any notification in the bell. An admin reverses a moderation action through the appeal flow, which stores the reversal notification with id = NULL. GET /api/v1/notifications now returns an item with id null; the Alpine bell validates the payload, the null id fails the schema, parseOr falls back to {items: []} - so the user's whole notification list renders empty (mentions, quest updates, everything) while GET /api/v1/notifications/unread-count still counts the unread row. The SSE stream poisons the same payload so the bell stops updating entirely, and the row is unreachable by id so read-all is the only way to clear it. Proposed fix: give the insert an explicit id (id: uid() as src/notifications/service/crud.ts:58 does, or crypto.randomUUID() as audit.ts:141 does) and close the type hole so the next omission cannot compile - the column has no DB default, so the generated type must be id: string rather than Generated`<string>`, and a forward migration should make notifications.id NOT NULL (SQLite requires a table rebuild) so a missing id fails at the database instead of storing NULL. Regression test: every row returned by the list route has a non-null id, and an insert without id is rejected.

**Context:**

Same defect class as `BUG-assistant-created-lore-entries-are-stored-with-a-null-id-so-.md`: a TEXT PRIMARY KEY with no DB default, written without an id. `notifyModeratorReversal` was the only production `notifications` writer that omitted it (`notifications/service/crud.ts:58` and `nsfw/moderation-service/audit.ts:141` both pass one).

The fix has two halves:

1. The insert site now supplies `id: uid()` (`src/nsfw/moderation-service/appeals-reversal.ts:143-147`). This closes the defect.
2. The type hole that let the omission compile (`id: Generated<string>` claims a DB default that no migration creates) is closed by the GENERATOR — `src/db/schema-*.ts` is regenerated from the migration chain, so a hand edit would be reverted by the next `db:sync-types` run.

The generator half is owned by a separate branch (TASK-generated-db-types-mark-every-primary-key-as-db-generated-so, issue `db7edfa`) and is deliberately NOT part of this commit: the general rule change breaks typecheck repo-wide, so it must land as its own change with its own sweep.

A forward migration making `notifications.id` NOT NULL was considered and deliberately NOT done: SQLite requires a full table rebuild for that, it would need a backfill of any already-stored NULL-id rows, and the compile-time guarantee (owned by db7edfa) already covers the failure mode at the source. The rebuild is a separate, riskier change; the ticket's own summary lists it as one option among several.

**Resolution:**

- Fix: `src/nsfw/moderation-service/appeals-reversal.ts:143-147` — the `notifications` insert now passes `id: uid()`; the `uid` import was added at `:13`.
- Type hardening is NOT in this commit: it belongs to TASK-generated-db-types-mark-every-primary-key-as-db-generated-so (issue `db7edfa`), which owns `scripts/generate-db-types.ts` and the generated `src/db/schema-*.ts`. Until that lands, `Notifications.id` remains `Generated<string>` and a future omission would still type-check — the regression test below is what guards it in the meantime.
- Test: `src/nsfw/moderation-service/appeals.test.ts` — "reversal notification is stored with a non-null id" (added next to the existing "reversal writes a notifications row for the original moderator" case). It drives the real reversal flow (`submitAppeal` → `reviewAppeal` → `executeReversal`), then asserts the stored row's `id` is non-null AND that the row returned by the public `NotificationService.list()` carries a usable id — the user-visible symptom the ticket describes (a null id fails the client's `NotificationListItem` validation and empties the whole list).
  - Before the fix: FAIL — `expect(received).not.toBeNull()` → `Received: null` (18 other tests in the file still passed).
  - After the fix: PASS (19/19 in the file).
- The pre-existing test "reversal writes a notifications row for the original moderator" was left untouched — its contract (a `notifications` row with `type = "appeal.reversed"` exists for the moderator) is unchanged.
