# BUG: World edit modal served blank fields and wiped world description/lore

**Status:** Done
**Priority:** high
**Effort:** Medium
**Epic:** epic-world-management-ui
**Caveats:** TOCTOU, security, authorization, parallelism, lock/unlock lifecycle, partial failure, rollback, stale state, data races, idempotency, observability

**Summary:**

Symptom: the world-detail page's Edit button opened a modal whose name/description/lore fields were all blank. Saving it silently wiped the world's description and lore.

Root cause: the Edit button loaded a STATIC, DB-less partial (src/partials/worlds/edit-modal.html) through the GET partials route (src/routes/views/plugin-static.ts:12-27 -> src/routes/views/static-partials.ts:14-35), which never resolves includes and never reads the world row - the input at :26 carried no value and the textareas at :31-39 and :48-56 were empty, and the text-toolbar includes at :41 and :58 were rendered verbatim. The form PUT to the world update route (src/partials/worlds/edit-modal.html:17) with those empty fields, and the handler writes any non-null field, so description and lore were overwritten with empty strings.

Fix: keep the modal and make it show the world's CURRENT values. The partial stays DB-less, so the modal prefills itself client-side: a new Alpine component (src/frontend/alpine/world-edit-modal.ts, mounted with x-data="worldEditModal()" on the modal root) reads the world id from the form's own PUT target (/api/v1/worlds/{{worldId}}) and loads the world through the access-checked GET /api/v1/worlds/:id (src/frontend/alpine/world-fetch.ts), writing name/description/lore into the three fields. The Save button ships disabled and is only enabled once the values are loaded, so a world that cannot be loaded can never be submitted empty. The server keeps its semantics - a non-null field is written as sent - so a field the user clears on purpose is still cleared; the accidental-empty path is closed on the client, the only side that can tell "cleared" from "never loaded".

Verification: src/frontend/alpine/world-edit-modal.test.ts mounts the component against the real API response shape and asserts the fields end up holding the world's current name/description/lore, that an untouched save submits them unchanged instead of clearing them, and that a world which fails to load leaves Save disabled and the fields empty; a fourth test asserts the served partial still wires the prefill and ships Save disabled, and a fifth asserts the name input's maxlength still matches the backend schema's Name.maxLength. The loaded row is decoded through a TypeBox schema (WorldRowSchema in src/frontend/alpine/world-edit-modal.ts) before any field is read - a payload that is not a world row fails closed (fields empty, Save disabled) instead of filling the form with guesses, and a sixth test asserts exactly that. Two further tests pin the id boundary: src/frontend/alpine/world-fetch.test.ts asserts the world id is URL-escaped into the request's path segment, and the modal test asserts the modal loads the world the form targets (an id carrying "/" stays ONE id - the last path segment would be another world). Both fail without their fix. bun test src/frontend/alpine, bun test src/routes/views, typecheck, typecheck:frontend, eslint, dprint, size and i18n gates green.

**Context:**

Why: the Edit button on the world-detail page loads a static, DB-less partial, so the modal's fields arrive blank; the PUT then writes those blanks over the world's row and the description and lore are gone. The full-page editor at /worlds/:id/edit already prefills from the same endpoint, so the fix reuses that data path instead of adding one.

What changed:
- src/frontend/alpine/world-edit-modal.ts (new) - the Alpine component plus prefillWorldEditModal(); loads the world with the existing fetchWorldJson helper and fills #edit-name, #edit-description and #edit-lore.
- src/frontend/alpine/index.ts - registers the module in the Alpine bundle.
- src/partials/worlds/edit-modal.html - x-data="worldEditModal()", id="edit-world-form", and a Save button that ships disabled and is enabled once the world is loaded.
- src/frontend/alpine/world-edit-modal.test.ts (new) - the regression test.
- src/partials/worlds/edit-modal.html, src/partials/worlds/create-modal.html, src/views/world-edit.html - the name input mirrors the API's limit (maxlength="255") on every world surface, so an over-long name cannot turn the whole save into a 422 that drops the description and lore edits with it.
- docs/frontend/worlds.md - documents the modal surface, its prefill and the fields' real limits.
- src/frontend/alpine/world-fetch.ts - the shared world-scoped fetch helper URL-ESCAPES the world id into its path segment (`encodeURIComponent`). The modal's id comes out of the DOM (the form's PUT target), so it is a value the page did not mint; HTML escaping (the server's `escapeHtml`) does not make a value safe in a URL path, and an id carrying "/" or "?" would otherwise retarget the request. Every caller passes the raw id, so this is the one place the segment is built.
- src/frontend/alpine/world-edit-modal.ts - the world id is read as EVERYTHING after the known `/api/v1/worlds/` prefix, not as the last path segment: an id carrying "/" would otherwise yield a different id than the form targets, and the modal would fill itself with another world's values. The API still owns the id's shape (a bad id answers 404 and the modal stays unsaveable).
- src/frontend/alpine/world-fetch.test.ts, src/frontend/alpine/world-edit-modal.test.ts - the regression tests for those two boundaries: the world id is URL-escaped into the path segment, and the modal loads the world the form targets (an id carrying "/" stays ONE id). Both fail without their fix.

Constraints: no new endpoint, no backend change, no new dependency - the modal is served by the static partial route, which has no database handle.

Backend authority: the API stays the source of truth for every field it writes - the route validates the body against WorldUpdateBody (name 1..255 via Name; description and lore any string, with "" meaning a deliberate clear) before the handler writes it, and the frontend now mirrors those limits exactly. The one rule with no server-side expression is "a client must not send a value it never loaded": an empty string is a legitimate clear, so the server cannot tell a clear-on-purpose from a clear-by-accident. Making that server-authoritative needs an API-contract change - WorldUpdateBody would grow explicit clearDescription/clearLore flags, the schema would reject an empty string otherwise, and every caller (the full-page editor, this modal, any external client) would have to adopt them. Named as the follow-up rather than done here: it changes a published contract beyond this defect.

Authorization confirmed (verified in code, not assumed): the modal's data source is the read route GET /api/v1/worlds/:id (src/routes/worlds/worlds-routes.ts:84-102 -> handleGetWorld, src/routes/worlds/worlds.ts:146-158), which gates on the shared requireWorldAccess (src/routes/worlds/access.ts:35-73). That check is row-level: it loads THAT world's owner_id and visibility and admits the owner, an admin holding admin.world, a world member, or any authenticated reader of a PUBLIC world (the synthetic guest tier included); everyone else gets 404 "World not found", so a denied reader cannot even learn that the world exists. The write path PUT /api/v1/worlds/:id gates on requireWorldOwner (src/routes/worlds/worlds.ts:175, src/routes/worlds/access.ts:84-99): owner or admin, otherwise 403. Existing route tests already cover both (src/routes/worlds/worlds-routes.test.ts:508-527 the guest and anonymous read tiers, :542-558 the guest mutation denial, :560-576 the registered stranger against a private world, and :62-101 the read response carrying the world's lore - the field the prefill writes). The client decides no access of its own: it renders what the API returned and fails closed, with Save left disabled, when the API says no.

Rejected: rendering the modal server-side (a route with a database handle plus the world access checks) - the client-side prefill reuses the already-shipped access-checked endpoint and needs no new route; deleting the modal in favour of the full-page editor (the original plan in this ticket) - that replaces the surface the world-detail page links to, which is outside this lane's scope, and the modal stays reachable from that page.

Still open (a separate defect, untouched here): the static partial route never resolves {{> ... }} includes, so this modal - and the world's create modal and create wizard - render the text-toolbar include verbatim.

Injection surface pinned (added in this lane): src/routes/worlds/worlds-injection.test.ts (new) asserts that the world id reaching GET /api/v1/worlds/:worldId - a path parameter that reaches the database as a query value - is BOUND and never concatenated: a SQL-shaped id ("x' OR '1'='1") answers 404 and leaks no row, a stacked statement ("x'; DROP TABLE worlds; --") cannot reach the database (the table still answers for the real world), and the list filter's LIKE value is bound the same way (a crafted pattern matches no world instead of returning every visible one). The queries themselves were already parameterized (Kysely .where("id", "=", worldId) / .where("name", "like", ...)); this test pins that they stay that way.

Parallel-safe test design (this lane's two test files): both files now document their resource contract and own only what they own. worlds-injection.test.ts creates a FRESH in-memory SQLite DB per test (createTestDb in beforeEach, destroyTestDb in afterEach - deterministic teardown that runs even when an assertion throws) and seeds its own user and canary world per test, so no test sees another test's rows, every test passes on its own and in any order, and the file never touches the process-global setTestDatabase override, a provider, a port or a file. world-edit-modal.test.ts OWNS the globalThis.apiFetch slot for the duration of one test and releases it in afterEach (the ambient apiFetch global is shared with every other suite in the worker), and installs the stub unconditionally so a prior suite's leaked stub cannot satisfy the component and silently pass the assertions.

API documentation (proposal, not enforced here): the world's read route declares its 200 response as t.Any() (src/routes/worlds/worlds-routes.ts:92), so the generated OpenAPI spec carries no shape for the world's row - a hand-maintained row shape in the spec would be exactly the copy that drifts. The repo already generates and serves the spec from the live route schemas (GET /api/v1/openapi/json, regenerated on every boot, api-doc-drift gate at path/method level), so the deliverable is a source-of-truth row schema, not a doc file. The generator (scripts/generate-db-types.ts) emits src/validation/db-schemas.ts from the migrations, but that schema is INSERT-shaped: nullable columns come out as t.Optional(t.String()) - absent, not null - while the row the API returns carries description/lore as null. The generated schema is therefore not usable as the response schema as it stands; the fix belongs in the generator (emit the read shape, or a nullable overlay), which is a shared-file change outside this lane's defect. Not done here for that reason, and the typed response was left as t.Any() rather than a hand-written copy.
