## Implementation Note (sdcpp-discovery, 2026-11-12)

- **Discovery probe** — `src/generation/image-engine/sdcpp-discovery.ts`: `probeSdCpp` GETs `/sdcpp/v1/capabilities` and reports reachability, latency, version (`version` or `build_info.build_number`), loaded-model `state`/`serverError`/`models` from the additive `runtime` field, as a discriminated union. Structured skip reasons: `invalid-base-url` | `unreachable` (transport failure) | `http-error` (non-2xx — a 404 from a non-sd.cpp HTTP server or a 503 while loading is NOT liveness) | `malformed-response`. Parsing is defensive; the probe never throws.
- **Admin discovery sweep** — `GET /api/admin/sd-status/sdcpp` (in `src/routes/admin/sd-status.ts`, admin.system-gated): probes every candidate — stored setups, config-file sdcpp providers, the `autoStart.sdCpp` instance — in parallel (`Promise.allSettled`), reporting `source` (`config`/`stored`/`auto-start`), `dispatching` (whether the generation path serves this instance now), and the structured reason when unreachable. Never echoes key material.
- **Setup surface** — `POST`/`DELETE /api/admin/sd-status/sdcpp/setup` (`src/routes/admin/sdcpp-setup.ts`) following the setup-providers pattern: TypeBox body schema, probe-gate BEFORE save (unreachable target → 502 with the structured reason, nothing stored), store validation in `src/generation/image-engine/sdcpp-setup.ts` (slug name, `validateProviderUrl` + explicit link-local/cloud-metadata rejection — the sync URL validator does not resolve DNS, so a literal metadata host passes it; defaults range-checked). Persisted in `system_config` under `sdcpp.<name>.config` (descriptor JSON) and `sdcpp.<name>.apiKey` (sealed — the key matches `SECRET_KEY_PATTERN`); list responses carry `hasApiKey` only. Empty `apiKey` clears a stored key.
- **Fallback skip wiring** — `generateImagesWithFailover` (`src/generation/image-engine/index.ts`) probe-gates sdcpp candidates (bounded by `min(provider.timeout, 3s)`): an unreachable instance is SKIPPED with the structured reason recorded on the failure outcome's new `attempts` field (`src/generation/image-engine/types.ts` `FailoverAttempt`), the walk continues to the next backend, and a provider that THROWS is converted to a failure outcome so one backend can no longer abort the whole walk. When every candidate is skipped, the outcome names each skip reason. `image-gen-route` merges stored setups into its candidates (`mergeSdCppSetups` — a stored setup replaces a same-name config provider), so a saved instance serves generation without a restart. Boot auto-discovery (`src/services/sd-discovery.ts`) gains the sd.cpp well-known port 9010 with `/sdcpp/v1/capabilities` as its health path.
- **Tests** — `sdcpp-discovery.test.ts` (probe parsing/reasons/URL joining), `sdcpp-setup.test.ts` (validation matrix, sealed-key round-trip, merge), `routes/admin/sdcpp-setup.test.ts` (auth, probe-gate 502, no-secret responses, delete), `sd-status.test.ts` (sweep auth + config/stored/auto-start shapes), `image-engine/index.test.ts` (skip-then-fall-through, http-status skip record, healthy-dispatch-no-probe). All green; full `bun run check` NOT run in this lane (operator lands).
- **Consumer rewire (wave 3)** — the remaining single-pick consumers now fall back to stored setups through one shared helper, `pickStoredSdCppProvider` (`src/generation/image-engine/sdcpp-pick.ts`): it materializes stored setups with the same `listStoredSdCppProviders` store read the generation path uses and probe-gates each candidate with the same discovery gate the failover walk applies (`sdCppSkipAttempt`, now exported from `src/generation/image-engine/index.ts`) — unreachable setups are skipped with the structured reason logged, never dispatched blind. Consumers: image-edit `SDServerEditProvider` (stored fallback tried once, and ONLY when no config-file sd provider exists at all — a config pick is authoritative even if its URL later fails validation, which keeps BYO credential resolution and dispatch on the same instance), image-edit BYO credential resolution (`resolveEditApiKey` resolves against a stored setup's name when no config-file provider exists, unprobed — the dispatch probe-gates), and emotion-avatar batch generation (`runBatchGeneration` picks stored after `pickSdProvider` misses). Config-file providers keep their precedence: `pickSdProvider` over the config list wins whenever it resolves; stored setups are strictly fallback. Matting (`src/generation/matting/factory.ts`) stays ComfyUI-only by design — there is no sd.cpp matting provider, so stored setups deliberately do not join that pick. Tests: `src/generation/image-engine/sdcpp-pick.test.ts` (healthy pick, structured skip + fall-through, purpose fit, no key material on the skip path).
- **ComfyUI surface + `/image` routing (2026-11-12, same lane)** — remaining-scope items (1) and (2) are closed: the setup store engine is family-generic (`sd-setup-store.ts`; `sdcpp-setup.ts`/`comfyui-setup.ts` are thin bindings, rows under `comfyui.<name>.config` + sealed `comfyui.<name>.apiKey` — the optional Bearer credential is the auth seam the ComfyUI client and video path already have, with `generateComfyUI` now forwarding `opts.apiKey ?? sdConfig.apiKey`), the probe is `probeComfyUI` against the native `GET /system_stats` readiness endpoint (`comfyui-discovery.ts`, same discriminated union and skip reasons as sd.cpp), admin surface is `GET /api/admin/sd-status/comfyui` (stored + config sweep, no auto-start — ComfyUI autoStart does not exist in the schema yet) and `POST`/`DELETE /api/admin/sd-status/comfyui/setup(/:name)` (same admin.system permission model, probe-gated save, metadata-host rejection), stored ComfyUI setups materialize onto `generateImagesWithFailover` via the same per-family discovery gate (`comfyUiSkipAttempt`; image-gen-route merges both families), and the `/image` ComfyUI-first opt-in is the `generation.imageRouting.comfyUiFirst` config knob (default OFF = config order; ON = `comfyUiFirstOrder` puts ComfyUI candidates first while the walk's gate still skips dead ones with structured reasons) — TASK-sd-cpp-provider.md carries the AC detail.
- **Remaining scope** (explicitly NOT done here): (1) matting remains ComfyUI-only (see above) — an sd.cpp matting provider would be new provider-registry scope; (2) `TASK-sd-multi-provider-text2img-fallback-documented-but-nonexiste.md`'s cited `image-edit-service/apply.ts` call site does not exist under that path — the image-edit pick now lives in `SDServerEditProvider` + `resolveEditApiKey`, both rewired; (3) ComfyUI auto-start lifecycle is `TASK-comfyui-first-class-standalone-auto-start-config-lifecycle.md` (no `autoStart.comfyUi` schema exists, so the sweep has no auto-start candidate); (4) image-edit/emotion-avatar stored fallback stays sdcpp-scoped (`pickStoredSdCppProvider`) — a ComfyUI fallback there is new scope.
