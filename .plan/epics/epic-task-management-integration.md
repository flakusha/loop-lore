# EPIC: Task Management Integration

**Status:** 📝 Draft
**Priority:** Medium
**Effort:** Medium
**Type:** Process / Tooling Epic
**Tags:** task-management, planning, workflow, tickets, integration, cli

## Summary

Research and define how the `task-management` skill (JSON-based, `.tmp/tasks/`)
relates to the existing `.plan/tickets/` system (markdown-based, git-tracked).
Produce integration guidance so agents can use the right tool for the right
granularity without duplicating state.

## Problem Statement

Two task-tracking systems coexist with no documented relationship:

| System | Location | Format | Tracking | Git-tracked |
|--------|----------|--------|----------|-------------|
| `.plan/tickets/` | `.plan/tickets/*.md` + `index.json` | Markdown + JSON index | Epics, tickets (TASK/FEAT/BUG), priority, epic linkage | Yes |
| `task-management` skill | `.tmp/tasks/{slug}/task.json` + `subtask_*.json` | JSON | Subtask deps, exit criteria, context files, parallel execution | No (`.tmp/` gitignored) |

This creates ambiguity: when should an agent create a `.plan/tickets/` entry vs
a `.tmp/tasks/` task? When do they cross-reference? What's the source of truth?

## Current State

### `.plan/tickets/` (established)
- ~150+ tickets (TASK-*, FEAT-*, BUG-*)
- Indexed in `index.json` (auto-generated by `bun run plan:sync`)
- Linked to epics via `epic` field
- Lifecycle: ticket → worktree → PR → merge
- State tracked via markdown content (no formal status field in most tickets)

### `task-management` skill (newer)
- JSON-based task + subtask files in `.tmp/tasks/`
- CLI: `bun .opencode/skills/task-management/scripts/task-cli.ts`
- Supports: dependencies, exit criteria, context/reference files, parallel execution
- Integrates with `TaskManager` subagent for breakdown
- Ephemeral by design (`.tmp/` is gitignored, scratchpad)

### Gap
- No documented mapping between ticket types and task-management granularity
- No workflow for "decompose a FEAT ticket into subtasks via task-management"
- Risk of agents creating parallel tracking that drifts

## Scope

### Research Deliverables

1. **Granularity Matrix** — document when to use which system:
   - `.plan/tickets/` → cross-session, git-tracked, epic-linked work items
   - `.tmp/tasks/` → single-session, fine-grained subtask decomposition with deps
   - Rule of thumb: ticket = "what to build"; task = "how to build it this session"

2. **Integration Pattern** — define how they reference each other:
   - Option A: ticket body links to task-management slug (`task: my-feature`)
   - Option B: task-management `context_files` references ticket path
   - Option C: task-management replaces ticket for implementation; ticket stays as epic ledger
   - Choose one, document it

3. **Lifecycle Mapping** — state transitions:
   - Ticket `open` → agent spawns task-management breakdown → subtasks execute → ticket `done`
   - Or: ticket drives directly, task-management only for complex multi-step features

4. **Agent Workflow Guide** — concrete instructions for AGENTS.md:
   - "When starting a FEAT ticket, check complexity. If >3 steps, create task-management breakdown first."
   - "When task-management task completes, update ticket status."
   - "Never create task-management entries for BUG tickets (single-fix)."

### Out of Scope
- Replacing either system (both have distinct value)
- Migrating existing tickets to task-management format
- Building a unified CLI (too early; pattern first)

## Acceptance Criteria
