# EPIC: Task Management Integration

**Overview:** (see sections below)


**Status:** Done
**Priority:** Medium
**Effort:** Medium
**Type:** Process / Tooling Epic
**Tags:** task-management, planning, workflow, tickets, integration, cli

## Goals

- Give agents one written rule for which tracker to reach for, so a ticket and a scratch task never both claim the same work.
- Make the plan index queryable by tag and binding, which is what tooling (`/find-work`, admin filtering, routing by tag) needs.
- Keep the plan index reconciled — the pre-existing orphan/phantom backlog that used to redden the `tickets` gate is resolved (the cleanup ticket closed Wontfix: the condition no longer exists).

## Summary

Research and define how the `task-management` skill (JSON-based, `.tmp/tasks/`)
relates to the existing `.plan/tickets/` system (markdown-based, git-tracked).
Produce integration guidance so agents can use the right tool for the right
granularity without duplicating state.

## Problem Statement

Two task-tracking systems coexist with no documented relationship:

| System | Location | Format | Tracking | Git-tracked |
|--------|----------|--------|----------|-------------|
| `.plan/tickets/` | `.plan/tickets/*.md` + `index.json` | Markdown + JSON index | Epics, tickets (TASK/FEAT/BUG), priority, epic linkage | Yes |
| `task-management` skill | `.tmp/tasks/{slug}/task.json` + `subtask_*.json` | JSON | Subtask deps, exit criteria, context files, parallel execution | No (`.tmp/` gitignored) |

This creates ambiguity: when should an agent create a `.plan/tickets/` entry vs
a `.tmp/tasks/` task? When do they cross-reference? What's the source of truth?

## Current State

### `.plan/tickets/` (established)

- Markdown tickets (TASK-*, FEAT-*, BUG-*, …), each with `**Status:**` / `**Priority:**` / `**Effort:**` headers
- Indexed in `.plan/tickets/index.json` (regenerated by `bun run plan:sync`; never hand-edited)
- Linked to epics via the `**Epic:**` header — the linkage gate reads that spelling only
- Lifecycle: ticket → worktree → PR → merge
- Tags are freeform (`**Tags:** a, b, c`); there is no closed tag vocabulary

### `task-management` skill (newer)

- JSON-based task + subtask files in `.tmp/tasks/`
- CLI: `bun ~/.config/opencode/skills/task-management/scripts/task-cli.ts` — the skill lives at user level (`~/.config/opencode/skills/task-management/`, with `SKILL.md`, `router.sh`, and `scripts/task-cli.ts`) and is **not vendored** in this repo: no `.opencode/` directory exists here and nothing under `.agents/skills/` shadows it.
- Supports: dependencies, exit criteria, context/reference files, parallel execution
- Integrates with `TaskManager` subagent for breakdown
- Ephemeral by design (`.tmp/` is gitignored, scratchpad)

### Code reality

There is no task-management system in `src/`. The only two files that touch the concept are
unrelated to tracking: `src/prompts/task-clarification.ts` (a prompt template) and
`src/aux-pipeline/task-detect.ts` (aux-task classification from prompt shape). Nothing in
`src/` creates, stores or resolves tickets or scratch tasks.

### Gap

## Scope

### Research Deliverables

1. **Granularity Matrix** — document when to use which system:
   - `.plan/tickets/` → cross-session, git-tracked, epic-linked work items
   - `.tmp/tasks/` → single-session, fine-grained subtask decomposition with deps
   - Rule of thumb: ticket = "what to build"; task = "how to build it this session"

2. **Integration Pattern** — define how they reference each other:
   - Option A: ticket body links to task-management slug (`task: my-feature`)
   - Option B: task-management `context_files` references ticket path
   - Option C: task-management replaces ticket for implementation; ticket stays as epic ledger
   - Choose one, document it

3. **Lifecycle Mapping** — state transitions:
   - Ticket `open` → agent spawns task-management breakdown → subtasks execute → ticket `done`
   - Or: ticket drives directly, task-management only for complex multi-step features

4. **Agent Workflow Guide** — concrete instructions for AGENTS.md:
   - "When starting a FEAT ticket, check complexity. If >3 steps, create task-management breakdown first."
   - "When task-management task completes, update ticket status."
   - "Never create task-management entries for BUG tickets (single-fix)."

## Ticket ↔ Task Contract (2026-10-10 — chosen and in force)

Grounded in the real `task-management` skill schema (user-level,
`~/.config/opencode/skills/task-management/`; its `scripts/task-cli.ts`
validator is the schema authority — `SKILL.md`'s examples lag it: subtasks
require a nullable `agent_id`, and the CLI runs under `bun`, not
`npx ts-node`). Task files: `.tmp/tasks/{slug}/task.json` (id, name, status
`active|completed|blocked|archived`, objective, `context_files`,
`reference_files`, `exit_criteria`, subtask/completed counts) and
`.tmp/tasks/{slug}/subtask_XX.json` (id `{slug}-{seq}`, seq, title, status
`pending|in_progress|completed|blocked`, `depends_on`, `parallel`,
`context_files`, `reference_files`, `acceptance_criteria`, `deliverables`,
`agent_id`, timestamps, `completion_summary`).

### Granularity matrix

| Dimension | `.plan/tickets/*.md` | `.tmp/tasks/{slug}/` |
|-----------|----------------------|----------------------|
| Question answered | WHAT to build (build ledger) | HOW to build it this session |
| Lifetime | Cross-session, permanent | One session (`.tmp/`, gitignored) |
| Git-tracked | Yes, reviewed in PRs | No — scratchpad |
| Linkage | `**Epic:**`, `**Related:**`, git issues | `context_files`/`reference_files` paths |
| Gating | `plan validate` gates | `task-cli validate` (schema, deps, cycles) |
| Granularity | Ticket-level work items | Atomic subtasks with dependency graph |
| Status vocabulary | Not Started/In Progress/Blocked/Done/Wontfix/Postponed | pending/in_progress/completed/blocked |
| Querying | `plan:report`, feature-matrix, `/find-work` | `task-cli status/next/blocked/parallel/deps` |

### Integration pattern — Option B chosen (task references ticket)

The ticket is the durable WHAT/ledger; the task breakdown is the session HOW.
Cross-referencing flows ONE way: `task.json`/`subtask` `context_files` and
`reference_files` name the ticket path (and any spec/source files); the ticket
carries no `.tmp/` slugs — its `**Related:**` must resolve to plan files, and
`.tmp/` is ephemeral, so a slug there would dangle and rot. This keeps the
git-tracked ledger authoritative and makes the session breakdown disposable
without touching ticket history. The durable proof of a decomposition lives as
a quoted fenced block in the ticket md, not as a pointer into `.tmp/`.

### Lifecycle mapping

```
ticket Not Started
  └─(agent: complexity >3 steps → decompose via task-management)─► ticket In Progress
       └─ subtasks pending → in_progress → completed (task-cli complete <feature> <seq> "summary")
             └─ all subtasks completed AND task.json exit_criteria met
                   └─(agent, same session)─► ticket Done (md Status; giwt sync/git issue reconcile)

reverse edges:
  subtask blocked (explicit) or no ready tasks → nothing to execute →
    ticket Blocked (agent updates md + giwt state) until unblocked
  session ends with subtasks open → ticket stays In Progress (ledger survives;
    .tmp breakdown is re-created next session or quoted into the ticket)
```

Who updates the ticket: the agent driving the session, at the moment of the
transition — In Progress when the decomposition is authored, Done only when
`exit_criteria` are verifiably met (never on subtask completion alone).

### Agent workflow guide

- Pick ONE primary tracker per piece of work; never duplicate state.
- FEAT/TASK spanning >3 steps → decompose into `.tmp/tasks/` first; BUG stays
  single-fix unless the fix spans >3 files.
- Work `task-cli next`; keep `task-cli validate` green; `complete` subtasks
  with real summaries.
- Update the ticket at transitions (In Progress / Blocked / Done) — the ticket,
  not `.tmp/`, is what operators see.
- Quote the decomposition (slugs + subtask structure) into the ticket md as a
  fenced block before the session ends; `.tmp/` will not survive.
