# Client Contract — `/api/v1/openapi/json`

**`GET /api/v1/openapi/json`** is the client contract.

Every client — TUI, SPA, mobile, script — generates a typed HTTP client from this
document rather than scraping HTML or duplicating route logic.

## Spec location and versioning

The spec is served **at runtime** by the `versionedOpenApiPlugin({ version: "1" })`
plugin (`src/routes/v1/openapi.ts:93-108`) mounted at
`src/routes/v1/admin-surface.ts:51`. It is **not** a committed artifact; it is
generated on each server boot from the live route schemas.

- Spec URL: `GET /api/v1/openapi/json`
- Scalar UI: `GET /api/v1/openapi`
- OpenAPI version: **3.1** (`openapi: "3.1.2"` in the document)
- API title: `Loop Lore API`
- Base server: `/api/v1` (relative URL; configure via `LOOP_LORE_API_BASE_URL`)

The spec is regenerated by `scripts/generate-openapi.ts`: boot the app, request
`GET /api/v1/openapi/json`, write the result. The committed fixture
`docs/reference/openapi.json` is gitignored; it is kept in sync by the
`api-doc-drift` CI gate.

## Base URL and environment

```typescript
// src/tui/chat/api.ts:7
export const API_BASE = process.env.LOOP_LORE_API_BASE_URL ?? "http://localhost:3000";
```

- Default: `http://localhost:3000`
- Configure: set `LOOP_LORE_API_BASE_URL` to the live server address.
- The spec's `servers[0].url` is `/api/v1` (relative), so clients append the
  base URL themselves.

## Authentication

The server uses **session-token authentication**. The credential is placed in the
`auth` option of `safeFetch`, not a header:

```typescript
// src/tui/chat/api.ts:33-34
auth: host.sessionToken ? { sessionToken: host.sessionToken } : undefined,
```

When `sessionToken` is set, the auth helper reads it from the `Authorization:
Bearer <token>` header. Unauthenticated requests receive a `401` response.
No cookie-based auth is used for the API surface today.

## Content negotiation

The server operates in **dual-mode**:

| Header | Behaviour |
|--------|-----------|
| `HX-Request: true` | Server renders an HTML fragment (htmx frontend) |
| `Accept: application/json` | Returns a plain JSON response where the handler supports it |
| Default (no header) | Full HTML page |

**The HTML views are NOT the contract.** They are an implementation detail of the
htmx/Alpine frontend. Clients MUST use `Accept: application/json`. See
`TASK-frontend-view-model-json-negotiation.md` for the JSON read-path.

## Response envelope

All JSON API responses follow this discriminated union:

```typescript
// src/tui/chat/api.ts:29-31 -- TUI parses this shape
type JsonResult<T> =
  | { ok: true; value: T }
  | { ok: false; error: { message: string; status: number } };
```

The TUI reads errors as `result.error.message` (`src/tui/chat/api.ts:42`).

## Live streaming: SSE only, no WebSocket

Live streaming uses **Server-Sent Events (SSE)**. There is **no WebSocket** mount:

- `src/routes/export-sse/` serves SSE streams for export progress.
- `src/elysia-app.ts` has **no** `.ws()` call (grep confirmed zero matches under `src/`).
- `src/transport/` is a standalone protocol library, not the server live transport.

SSE event types from export-sse handler schemas:

```typescript
type ExportEvent =
  | { type: "started"; exportId: string }
  | { type: "progress"; percent: number; message: string }
  | { type: "completed"; downloadUrl: string }
  | { type: "error"; message: string };
```

SSE replay semantics are not documented. A new client should treat each stream as
ephemeral and re-poll to recover state.

## Known gaps for non-browser clients

### CORS -- confirmed absent

No CORS middleware is present in `src/`:

```bash
grep -r "Access-Control" src/  # zero matches confirmed
```

An out-of-origin client will receive a browser-enforced CORS block.
`TASK-cors-middleware.md` is filed under `epic-headless-alternative-frontends.md`.

### CSRF / credentials semantics

The server applies CSRF double-submit cookie protection via
`src/middleware/csrf-plugin.ts`. Non-browser clients must either:

- Include the `csrf_token` cookie and send `x-csrf-token` on state-mutating
  requests (`POST`, `PUT`, `PATCH`, `DELETE`); or
- Use a route listed in `CSRF_EXEMPT_ROUTES` (`src/middleware/csrf.ts`) which
  bypasses the check.

### SSE replay

SSE streams are not idempotent. Disconnecting mid-stream requires re-polling the
originating endpoint to recover state.

## Reference client: the blessed TUI

The **TUI** (`src/tui/`) is the working non-htmx client. It implements auth via
`auth: { sessionToken }` and reads `API_BASE` from `LOOP_LORE_API_BASE_URL`.
Any new client should follow the same pattern.

## Generate a client

```bash
# Fetch the spec from a running server
curl -s http://localhost:3000/api/v1/openapi/json > openapi.json

# Generate a typed client (openapi-typescript not currently in deps)
npx openapi-typescript openapi.json --output src/client.ts
```

No generated client is committed. The `spec-drift` check in `scripts/check/`
fails when the served spec is no longer valid OpenAPI 3.1 or drops required paths.

## Required paths

The spec must contain these paths (verified by `scripts/check/spec-drift.mjs`):

| Path | Why required |
|------|-------------|
| `/api/v1/chats` | List/create chats |
| `/api/v1/chats/{id}` | Single chat CRUD |
| `/api/v1/chats/{id}/messages` | Message send/receive -- TUI primary path |
| `/api/v1/actors` | Actor listing |

If any are absent, the check exits non-zero.
