# Entity State Machine & Storage Model

## Principle

No hard deletes of user-generated content through normal UI actions. Every entity transitions through a state machine. The only way to permanently remove data is an explicit admin "purge" action that requires typed confirmation.

This applies to: messages, chats, characters, assets, worlds, and generation attempts.

---

## Base State Machine

All user-facing entities share a common state spine with optional extensions. The general flow:

**active** is the default state (visible, usable). A user action transitions to **archived** (hidden but recoverable). An admin or chat master can restore back to **active**, or perform a **purge** (permanent, irreversible removal, requires typed confirmation). Transient entities may also start in a **pending** state before becoming **active**, or enter a **failed** state on error with the option to retry.

---

## Entity-Specific State Machines

### Messages

State transitions: `active` → `archived` → `active` (restore) or `purged` (admin purge-archived).

- `active`: visible in chat timeline, participates in active path
- `archived`: hidden from timeline, has `archived_at` timestamp. Recoverable by admin/master via "show archived" toggle
- `purged`: permanent removal. Only via bulk "Purge archived" action. Irreversible.

**Parent-child cascade**: archiving a parent message archives all descendants (see [archiving.md](./chat/archiving.md) for full rules). Restoring a parent restores descendants.

---

### Generation Attempts

State transitions: `pending` → `processing` → `completed` or `failed`. From `failed`, can transition back to `pending` (retry). From any terminal state (`completed`, `failed` without retry), eventually transitions to `ttl_expired` (garbage collected after 1 hour).

- `pending`: queued but not yet picked up by worker
- `processing`: actively being generated by LLM/image backend
- `completed`: result stored, referenced by the message record
- `failed`: error occurred. Can be retried (back to `pending`)
- `ttl_expired`: row eligible for garbage collection. Not user-visible — the `generation_attempts` table is internal

**Storage**: `generation_attempts` table is the only entity with automatic TTL-based cleanup. Entries older than 1 hour are periodically purged regardless of state. This keeps the table lean — it's operational, not archival.

---

### Chats

State transitions: `active` → `archived` → `active` (restore) or `purged` (admin purge-archived).

- `active`: visible in sidebar, accessible via URL
- `archived`: hidden from sidebar, not accessible via normal navigation. Admin/master can view archived chats via a toggle. Recoverable.
- `purged`: chat + all its messages permanently removed. Requires typed confirmation.

**Cascade**: archiving a chat archives all its messages (they keep their individual `archived` state, but the chat-level archive is an additional filter — messages in an archived chat are hidden even if they were individually active). Restoring the chat restores message visibility.

---

### Characters

A character transitions through these states:

1. **`active`** (default) — Visible in character browser, available for new chats
2. **→ `archived`** — User action hides from browser. Existing chats still accessible, character still responds in those chats
3. **→ `active`** — Admin/master restores from archived view
4. **→ `purged`** — Admin only, typed confirmation required. Character + all associated chats permanently removed

**Note**: archiving a character does NOT archive its chats. The user can still access existing conversations.

---

### Assets

An asset transitions through these states:

1. **`uploading`** — File transfer in progress from client to server
2. **→ `ready`** — Upload succeeded, file available, asset usable and visible in gallery
3. **→ `archived`** — Hidden from gallery, not deletable by regular users. Admin/master can restore
4. **→ `purged`** — File deleted from storage + DB record removed. Irreversible

**Error paths:**

- From `uploading` → **`failed`** — Upload or processing error. Retryable: `failed` → `uploading` (starts fresh upload)
- From `failed` → **`ready`** — Retry succeeds, asset becomes usable

**File cleanup**: when an asset transitions to `purged`, the actual file on disk (or in object store) is deleted. Archived assets keep their file.

---

### Worlds

A world transitions through these states:

1. **`active`** (default) — Visible in world browser, selectable during chat creation
2. **→ `archived`** — Hidden from world browser. Existing linked chats still work and still reference the world's lore
3. **→ `active`** — Admin/master restores from archived view
4. **→ `purged`** — Admin only. World + all locations + lore permanently removed

**Cascade:** archiving a world archives all its locations. Restoring the world
restores its locations. Purging a world purges all locations, lore entries, and
linked chat references.

### Locations

A location transitions through these states:

1. **`active`** (default) — Visible in world detail, selectable for chat binding
2. **→ `archived`** — Hidden from world detail. Chats bound to this location
   still work (the location reference persists, but the location is not
   selectable for new chats)
3. **→ `active`** — Admin/world owner restores from archived view
4. **→ `purged`** — Admin only. Location + its gallery assets permanently removed

**Cascade:** archiving a location does NOT archive its chats. Chats bound to an
archived location remain accessible to their participants. The location just
cannot be bound to new chats while archived.

## State Transitions: Who Can Do What

| Transition           | Who can trigger                                           | UI action                                             |
| -------------------- | --------------------------------------------------------- | ----------------------------------------------------- |
| `active → archived`  | Message author (own), chat master, admin                  | Delete / Archive action                               |
| `archived → active`  | Chat master, admin                                        | "Restore" button in archived view                     |
| `archived → purged`  | Admin only                                                | "Purge archived" action, requires typing confirmation |
| `active → purged`    | Not available via UI (always goes through archived first) | —                                                     |
| `pending → failed`   | System (error)                                            | Automatic                                             |
| `failed → pending`   | Any participant                                           | "Retry" / "Regenerate" button                         |
| `uploading → ready`  | System (success)                                          | Automatic                                             |
| `uploading → failed` | System (error)                                            | Automatic                                             |
| `failed → uploading` | Asset owner                                               | Retry link in error state                             |

**Location-specific transitions:**

| Transition          | Who can trigger    | UI action                            |
| ------------------- | ------------------ | ------------------------------------ |
| `active → archived` | World owner, admin | Archive action in world detail       |
| `archived → active` | World owner, admin | Restore in archived locations view   |
| `archived → purged` | Admin only         | Purge action with typed confirmation |

## Storage Implications

- All state-transitioning entities store: `state TEXT NOT NULL DEFAULT 'active'` and `archived_at TEXT` (nullable, ISO 8601 timestamp)
- Archived rows are excluded from all normal queries via `WHERE state = 'active'` (or `WHERE state != 'archived'`)
- Index on `(state, user_id)` for efficient filtering in sidebar / gallery queries
- `generation_attempts` is the only table with TTL-based automatic cleanup (1 hour). All other entities require explicit action to transition to `purged`.
- The `purge_archived` action is a single transaction: `DELETE FROM messages WHERE state = 'purged' AND archived_at < now() - interval '30 days'` (30-day retention before final cleanup prevents accidental permanent loss even after purge)

---

## Why Enum State Machine Instead of Hard Deletes

| Concern               | Hard delete                                              | State machine                                    |
| --------------------- | -------------------------------------------------------- | ------------------------------------------------ |
| Accidental data loss  | Permanent, unrecoverable                                 | Recoverable by admin                             |
| LLM context debugging | Impossible — context chain broken                        | Archived messages preserve the chain             |
| Undo for users        | Not possible via UI                                      | "Restore" button works                           |
| Orphaned resources    | Easy to create (delete parent without cleaning children) | Cascade rules enforced                           |
| Storage growth        | Minimal                                                  | Slightly larger (archived rows) but acceptable   |
| Query complexity      | Simple (`WHERE id = ?`)                                  | Slightly more complex (`WHERE state = 'active'`) |
| Purge compliance      | Easy                                                     | Requires explicit action                         |
