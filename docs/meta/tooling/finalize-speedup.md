# Finalize Speedup

Where the time and the memory go in `bun run check` (and therefore in
`giwt finalize`), measured on this host, and what can safely be cut.

Every number below cites the artifact it came from. Anything not measured on
this host is marked **UNMEASURED** and is a proposal, not a result.

**Where the implemented scopes live.** The diff-scoped `lint - eslint` and
`md - lint` described in §4 and §8 are shipped code: `bc2f3f405` (from
`finalize-perf`, where it was `9318f1d0`) adds
`scripts/check/parallel/gates-scope.mjs` and its test and calls
`applyDiffScopedStaticGates(checks)` from `gates.mjs`. It is on `dev`, so every
command in §1 runs in the tree you are reading.

## 1. How to reproduce

```bash
# Per-gate duration table across every retained run report (writes .tmp/prof-table.md)
bun .tmp/finalize-profile.ts

# Wall clock + peak RSS of any gate command, measured the way the runner runs it
# (`bash -c` under /usr/bin/time -v, so the peak covers the whole process tree)
bun .tmp/finalize-profile.ts --measure "bun run lint:eslint"
bun .tmp/finalize-profile.ts --measure "bun run lint:oxlint"

# The two scoped-vs-full lint numbers quoted in §2 and §8
bun run lint:eslint                                   # 18.4s / 19395 MB
bunx eslint --concurrency=8 <the five files below>     # 5.8s / 2137 MB
#   scripts/check-parallel.mjs scripts/check/parallel/report.mjs
#   src/validation/schema-fuzz.generated.test.ts
#   .plan/feature-matrix.md
#   .plan/tickets/TASK-simplification-cleanup-ranked-execution-order-and-dead-vs-un.md

# The scoping guard rails, no gate spawned
bun test scripts/check/parallel/gates-scope.test.mjs
```

`git diff --name-only HEAD~4 HEAD` on `dev` at `bdb8f6847` supplies that
five-file list, so the scoped run covers the same paths a `--diff-base`
finalize would narrow to for that commit range.

Host: 32 cores, 61 GiB RAM, 3 GiB swap (`free -g`, measured 2026-10-12).

**`.tmp/finalize-profile.ts` and `.tmp/prof-table.md` are git-ignored scratch
and may be gone.** They were never committed, so a fresh clone, a
`giwt clean --apply`, or any scratch prune turns the first three commands above
into `file not found` — and the same prune takes the corpus they mine:
`scripts/check/parallel/retention.mjs` prunes `.tmp/run-*/` and old
`check-report-*.json` on every check run, and `giwt clean` keeps only the newest
`checkReportKeep` reports. **Treat every duration in §2 as unreproducible once
that corpus is gone**, not as a number you can re-derive.

What to do instead, in order of preference:

1. **Re-measure from scratch** — the per-gate wall clock and peak RSS do not
   depend on any retained artifact. Time each gate the way the runner runs it:
   `/usr/bin/time -v bash -c '<the gate command from gate-table.mjs>'`, which
   covers the whole process tree. Rebuild the §2 table from those runs.
2. **Re-derive from retained reports** *if any survive* — every report carries
   `checks[].durationMs` (`scripts/check/parallel/report.mjs:201`), so a partial
   corpus still gives partial medians. A rebuilt table over a smaller corpus is
   not comparable to the one quoted here; say so rather than splicing it in.
3. **Do not** trust the quoted figures to still describe this host. They were
   measured 2026-10-12 on the host described below; a reader in a later session
   must re-measure before reusing them.

The profile script was never versioned because it is ~180 lines of
`readdirSync` + a percentile and this section documents it. That trade is fine;
promising the reader a fresh run against a pruned corpus was not.

## 2. Measured baseline

Corpus: 22 reports in `.tmp/check-report*.json`, all `branch=dev mode=plain`,

`75325-mv2eyoyu` … `1488199-mv4sis10`. Source: `.tmp/prof-table.md`,

is a `giwt finalize` Step-2 run.** Finalize runs inside `tree/<branch>/`, so

*unscoped* cost, which is what a dev-side or `--force` run pays and what the

2. **`lint - eslint` could not fail on the measured tree.** It exits 0 with 2352

   not of the script: `local/no-extensionless-require` has since been registered
   at `"error"` (`5a9e80a3a`), so the gate is failable today.

## 3. Lint: eslint → oxlint

Already partly done, and further than the gate table admits: `oxlint.config.ts`
exists and enables `typescript`, `unicorn`, `import`, `oxc` with correctness as
error. `eslint.config.mjs:99` says "Minimal rules -- oxlint handles most;
ESLint only for what oxlint can't do", and the oxlint config explicitly omits
`typeAware` ("tsc handles type checking"). The gate table keeps `lint - eslint`
because oxlint is "manual; the canonical runner does not report it as
correctness evidence" (`gate-table.mjs:29`).

Measured: oxlint is 0.5s / 788 MB against eslint's 18.4s / 19 395 MB — a 37x
wall-clock and 25x memory difference, on the same tree, same host.

**What a swap would lose** (this is why it is documentation-only this round):

- **The local rule.** `eslint.config.mjs:21,82-86,190` registers
  `local/options-object-params`, implemented in
  `src/eslint-rules/options-object-params.mjs`. oxlint cannot run a bespoke
  ESLint rule; it has no plugin API for one. This is a project convention
  (`.agents/references/recommendations.md`) with no oxlint equivalent.
- **Markdown code blocks.** `eslint-plugin-markdown` (`eslint.config.mjs:16`,
  158-169) lints TS/JS fenced blocks inside `.md`. oxlint has no equivalent, and
  `lint:oxlint` additionally ignores `**/*.test.ts` and `tests` entirely, so
  `tests/**` would stop being linted at all.
- **jsdoc + sonarjs.** `jsdoc/require-{param,returns,throws}`
  (`eslint.config.mjs:225-227`) and the `sonarjs` recommended plugin have no
  oxlint counterparts.
- **Typed linting.** `eslint.config.mjs:172-178,261-267` sets
  `parserOptions.project` for `src/**` and `src/frontend/**`, so the ESLint run
  is type-aware. `oxlint.config.ts:11-13` deliberately omits `typeAware`.
  Anything currently caught only by a typed rule would be lost.
- **A clean baseline.** oxlint exits 1 today with 49 errors — for example
  `src/logger/formatters.ts:30` `no-control-regex`,
  `src/generation/workflow-substitutor.ts:88` `only-used-in-recursion`,
  `src/chat/moderation.ts:272` `no-useless-fallback-in-spread`. A swap means
  fixing or allow-listing those first, or the gate is red on day one.

Blocker list for the swap, in order: (a) resolve the 49 oxlint errors;
(b) re-implement `local/options-object-params` as an oxlint plugin, or accept
losing it; (c) decide the `tests/**` and `**/*.test.ts` gap; (d) decide the
markdown-code-block gap; (e) re-baseline. That is a migration project, not a
gate tweak. **Do not attempt it inside a finalize cycle.**

## 4. Scoping gates to the merge

`--diff-base` today scopes exactly two gates, both built in `gates.mjs`:
`coverageCommand()` (test set AND floor) and `e2eBrowserCommand()` (spec set).
Everything else is the static registry in `gate-table.mjs`, unchanged.

| gate | file-list scoping possible? | mechanism | must stay project-wide because |
| --- | --- | --- | --- |
| lint - eslint | yes | append the changed `ts/js/md` paths to the same `bunx eslint --concurrency=8` invocation | typed rules read the whole program (`parserOptions.project`), so a changed shared type can newly violate a rule in an UNTOUCHED file. Implemented with a full-run fallback on any config change. |
| md - lint | yes | `markdownlint-cli2 <changed .md>` | markdownlint has no cross-file rule; every configured rule is per-file. Implemented, same fallback. The scoped invocation still auto-discovers `.markdownlint.json`: that file only DISABLES rules (MD013, MD033, MD041, …) and this doc has 34 lines over 80 chars, so a run that missed the config would have failed MD013. It passed, which is the proof. |
| format - dprint | yes | `dprint check <paths>` | per-file formatter. **Not implemented**: 0.2s median, nothing to win. |
| mermaid - lint (mmdlint) | yes | `mmdlint <changed .md>` | per-file parser. **Not implemented**: 0.7s median. |
| typecheck x4 | **no** | — | `tsgo --noEmit -p <tsconfig>` is whole-program by construction; `type-coverage` computes a ratio over the whole project, and a `--files=` subset would change the denominator, i.e. the FLOOR would silently move. |
| dead - code (knip) | **no** | — | knip resolves an import graph: a deleted file changes the reachability of every importer. |
| jscpd ratchet | **no** | — | clone detection compares pairs ACROSS files; the baseline is a project-wide count. |
| size / size - strict | **no** | — | the threshold is per-file but the gate's purpose is catching NEW violations; scoping it would hide the untouched violators that exist today. |
| wiring, api-doc-drift, db-schema, i18n, test-gaps | **no** | — | each reconciles two trees against each other (routes vs services, spec vs doc, schema manifest vs DB, locales vs en.json, exports vs baseline). |
| plan - validate, plan sync, backlog, code-map, matrix | **no** | — | `.plan/` is reconciled against git issues and a generated index; a partial scan is not a reconciliation. Already ADVISORY for this reason. |

### Blindspots of the two implemented scopes

- **Untouched files are not re-linted.** Accepted on the premise that `dev`
  lints on its own merges, so the branch only adds new violations. That premise
  fails if a change makes an untouched file violate a rule — most concretely a
  changed exported type that newly triggers a typed rule in a caller.
- **Renames.** `changedFiles()` uses `git diff --name-only`
  (`context.mjs:114`), which reports the DESTINATION only. The old path is
  invisible; since it no longer exists on disk there is nothing left to lint, so
  a pure rename is covered. A rename that changes which config block a file
  lands in (`files: [...]` entries in `eslint.config.mjs`) is NOT covered — that
  is a config-change case and falls back to full.
- **Mode-only and type-only diffs** are indistinguishable here: any entry in
  the changed list makes the file lintable, so they are covered.
- **Untracked files** are absent from `CHANGED_FILES` (`context.mjs:85-87`
  documents this) — an un-`git add`ed new source file is not gated. Pre-existing
  behaviour, unchanged, and it applies to every scoped gate in the registry.
- **Config changes** fall back to the full run by construction
  (`SCOPE_BREAKERS` in `scripts/check/parallel/gates-scope.mjs`):
  `.markdownlint.json`, `dprint.json`, `eslint.config.mjs`, `oxlint.config.ts`,
  `package.json`, and the four `tsconfig*.json`.
- **Shell safety.** The gate command runs through `bash -c`
  (`scripts/check/gate-timeout.mjs:71`), so a changed path outside
  `[A-Za-z0-9._/@-]` forces the full run rather than being quoted.
- **Empty and oversized sets** fall back to the full run. An empty file list
  would exit 0 having linted zero files — the same NOOP_OK false-green the
  runner already guards against in `runCheck` (`runner.mjs:150`).

## 5. Test parallelism: the shared state, traced

Before proposing any concurrency, the hazards. Each is a file in this repo, and
each is currently mitigated *per worker process*, not per file.

1. **The DB override is a module-level singleton.** `src/db/index.ts:81`
   holds `let testDatabaseOverride`, returned by `getDatabase()` at
   `src/db/index.ts:117-118`. Its own comment (`:86-88`) records the bug:
   "Process-global under non-isolated runners; tests MUST clear it in
   afterAll/finally ... Bun's `--isolate` is best-effort". `createTestDb()`
   (`src/test-utils/create-test-db.ts:28-45`) builds a fresh `:memory:` Kysely
   per call and never touches the override, so most files are clean; the files
   that DO set it (`src/db/migrations.test.ts`,
   `src/db/migration-roundtrip.test.ts`, `src/db/migration-021-*.test.ts`) clear
   it in `afterEach`/`afterAll`. A test that throws before its cleanup leaks the
   override into the next file in the SAME worker process.
2. **`mock.module` is process-global.** 118+ files call it
   (`src/config/hot-reload.test.ts:54` even stubs `node:fs`). Under
   `--parallel=N`, N is the isolation boundary — files sharing a worker share
   the mock registry, and a stub registered without a matching restore
   (`src/chat/service/ownership.test.ts:368` restores in `finally`; many others
   do not) outlives its file.
3. **`process.env` mutation in tests.** e.g.
   `src/memory/embeddings.test.ts:139,191-192` sets `OLLAMA_BASE_URL`,
   `EMBEDDINGS_API`, `OLLAMA_EMBED_MODEL` in `beforeAll` and restores only
   some of them; `src/routes/auth/login.test.ts:382-413` flips `NODE_ENV` per
   test. `tests/setup-globals.ts:14-18` sets `LOOP_LORE_DB_PATH` once per
   process, keyed `pid-Date.now()`, which is correct across workers and shared
   across files inside one.
4. **Fixed temp paths.** `src/generation/matting/job-store.test.ts:33,82` uses
   `/tmp/loop-lore-jobstore-test` and `/tmp/loop-lore-jobstore-test-2`;
   `src/characters/services/emotion-avatar-service/*.test.ts` uses
   `/tmp/test-uploads`. Two concurrent runs of the same file, or two files
   sharing a directory, collide. They are not pid-qualified.
5. **Ports.** No hardcoded LISTEN port in tests: `src/memory/embeddings.test.ts`
   and `rerank.test.ts` bind a real server and read `server.port`. The fixed
   ports in the tree (`7860`, `9010`, `8188`, `3000`) are config VALUES passed to
   fetch stubs, never bound.

**Verdict: parallel unit tests are not proven safe on this host.** The known
skill ("bun tests pass alone yet fail together") and hazards 1 and 2 are the
mechanism; `--parallel` is already the default for `bun run test:unit`
(`package.json`, `TEST_JOBS=4`) and for the coverage gate, so this repo is not
in the state AGENTS.md describes as "forced serialized" for the test FILE
level — it is serialized at the GATE level (`HEAVY_NAMES` in `runner.mjs:201-206`),
which is a different thing. Smallest fix per hazard: (1) clear the override in
an `afterAll` registered before the tests run, not in the cleanup path;
(2) move the `mock.module` calls behind the `STRICTLY_ISOLATED` guard that
several files already use; (3) `pid`-qualify every fixed temp dir. All three are
unstarted; **UNMEASURED**.

## 6. Coverage gate: is the RUN scoped or only the FLOOR?

Both, under `--diff-base`; neither, without it. `gates.mjs:59-96`:

- plain mode runs `tests/e2e/` plus every `src/**/*.test.ts` and floors whole
  modules — the RUN is the whole suite (153.2s median, §2).
- diff mode runs every test under each touched top-level `src/` module and
  floors each touched `src/` file individually via `--files=`
  (`scripts/check/coverage.mjs:53-61`).

So AGENTS.md's "`bun run check --diff-base <ref>` scopes the COVERAGE gate"
is accurate for both halves. What is worth saying out loud: **the policy is
per-module, but the unscoped RUN is what a dev-side check pays**, and that is
the 36% line in §2.

## 7. Post-merge dev validation

What must run on `dev` after the merge lands, and whether it can move into the
worktree:

| post-merge step | can it move pre-merge? | why |
| --- | --- | --- |
| plan reconciliation (`plan - validate`, `plan - sync`, `plan - matrix`, `code-map - freshness`, `backlog - index`) | **no** | they reconcile `.plan/` against the git issue CLI and against generated artefacts of the MERGED tree. Pre-merge they would reconcile the branch's view and then go stale at the merge — which is exactly why all five are already in `ADVISORY_GATES` (`gate-table.mjs:164-197`) and reconciled after. |
| jscpd ratchet | **no** | clone count is a project-wide number over the merged `src/`; already ADVISORY for the same reason. |
| `dead - code (src files)` | **no** | knip reachability changes at merge time; already ADVISORY, and per `gate-table.mjs:183-195` currently red. |
| api-doc drift, db schema gate, fuzz-generated, i18n reconcile | **no** | each regenerates from the merged sources and diffs against the committed artefact; the artefact can only be final once the merge is. |
| the whole static set (typecheck x4, lint, dprint, md-lint, size, wiring) | **already pre-merge** | these run in the worktree (Step 2) and are merge-order independent; `api - doc drift` regenerates from tracked sources in the same commit that would have to touch them (`gate-table.mjs:69-74`). |
| coverage + browser baseline | **already pre-merge** | already scoped to the merge via `--diff-base`; the unscoped re-run on dev is the duplication worth dropping, and it is a `--gates` decision on the dev side, not a code change. |

Nothing moves. The finding is the opposite of the brief's hypothesis: the
gates that would benefit from moving earlier are the ones already in the worktree,
and the ones still on `dev` after the merge are the ones that CANNOT move.
